## What to add

### Parallel loops
- Add **one** `#pragma omp parallel for` around the OUTER loop that iterates across independent work units (rows, particles, pixels, contiguous slabs). This applies to both SIMD kernels and vetoed scalar kernels.
- Make sure there are at least 4–8 work units per thread (thread count is in the OpenMP launch block). If the outer loop alone has fewer iterations (e.g. a tile loop), use collapse(2) or collapse(3) over perfectly nested independent loops instead of parallelizing an inner loop.
- Do NOT place `#pragma omp parallel for` INSIDE a SIMD inner loop. The outer loop distributes chunks to threads; each thread runs the SIMD (or scalar) inner loop on its chunk.
- **One region.** Do not split the main loop and a 0–7 element tail into two `parallel for`. The tail stays inside the same function (scalar or masked), not in a second parallel region.
- Use `schedule(static)` for uniform work; `schedule(dynamic, chunk)` for variable work.
- Always use `default(none)` with explicit `shared(...)`, `private(...)`, `firstprivate(...)`, or `reduction(...)`. Do NOT list `const` or `constexpr` variables in data-sharing clauses.
- Declare SIMD register variables (`__m512d`, `__m256d`) as locals **inside** the parallel region rather than listing them in `private` if the compiler rejects those types in a clause.

### Reductions
- Use OpenMP `reduction(+:var)` for scalar accumulators that sum across iterations.
- For reductions that already use SIMD horizontal sums per iteration, keep the per-iteration SIMD reduction and add an OpenMP scalar reduction over the per-thread partial sums.

### Timing
- Replace any `std::chrono` or `clock_gettime` timing with `omp_get_wtime()`.
- Only one thread prints timing: check the thread id, or print after the parallel region has ended.

### Data sharing
- Large arrays passed as pointers are `shared` and safe when each iteration writes disjoint elements.
- Loop indices, per-thread accumulators, and temporaries are `private`.
- Broadcast constants computed before the parallel region with `firstprivate`, or leave them outside.

## Input data generated with a pseudo-random generator
If the program fills its input data with a pseudo-random generator (rand, random, drand48, rand_r, std::mt19937 / std:: distributions, or a hand-written generator), that generation code must produce exactly the same values, in the same order, as in the input program:
- Do NOT put it inside an OpenMP parallel region and do NOT split it across threads.
- Do NOT split it across MPI ranks, skip generator calls, reseed, or reorder which array is generated first.
- With MPI, every rank runs the original generation code unchanged (full arrays, same order) and then uses its own slice; this happens outside the timed region, so it does not affect the measured time. If the arrays are too large to replicate, rank 0 runs the original generation code and distributes the slices with MPI_Scatterv / MPI_Bcast, also outside the timed region.
- This applies only to data generation. The timed kernel is what you parallelize.
- If the generator is called INSIDE the timed kernel, keep its sequence of calls serial and identical to the input program.

- Do NOT add `#pragma omp simd`.
- Do NOT add a second parallel region for a 0–7 element tail.
- Do NOT add MPI.
- Do NOT change I/O, output format, or a checksum that sits outside the timed kernel.
